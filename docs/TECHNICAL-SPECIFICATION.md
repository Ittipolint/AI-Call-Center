## 1. Purpose

เอกสารนี้แปลง Requirement Specification ที่ได้รับอนุมัติแล้วเป็นรายละเอียดเชิงเทคนิคสำหรับการพัฒนา AI Call Center โดยมีเป้าหมายให้ Codex สามารถใช้เอกสารนี้เป็น implementation baseline ได้โดยไม่ต้องตีความ architecture หลักใหม่

ระบบต้องเป็น **configuration-driven, model-agnostic, RAG-grounded, session-isolated และ scalable** โดยเริ่มจาก 1 concurrent caller และสามารถขยายเป็นหลาย concurrent callers ในอนาคต

ระบบ Phase 1 เป็น **Browser-based voice application** ไม่ใช่ PSTN/SIP phone system โดยรับเสียงจาก microphone หรือ audio file ผ่าน Web Browser

# 2. Architecture Decisions

| Area | Decision |
|---|---|
| Frontend | Next.js + TypeScript |
| Frontend UI | React + Tailwind CSS + component library ตามความเหมาะสม |
| Main API | Python FastAPI |
| Realtime Gateway | Node.js + WebSocket (`ws`) |
| AI Orchestrator | Python service |
| STT | Whisper-family local model through adapter; default candidate `faster-whisper` with a multilingual model |
| LLM | Local 4B–8B instruct model; default candidate `Qwen3-8B` or equivalent validated model |
| Embedding | Multilingual embedding model; default candidate `BAAI/bge-m3` |
| Reranker | Optional multilingual reranker; default candidate `BAAI/bge-reranker-v2-m3` |
| TTS | Local TTS adapter; default candidate `Kokoro` or equivalent multilingual-capable implementation validated for Thai/English/Chinese |
| OCR | OCR adapter; default candidate PaddleOCR |
| Database | PostgreSQL |
| Vector Search | PostgreSQL + pgvector |
| Cache / Queue | Redis + Celery-compatible Python workers |
| Object Storage | MinIO (S3-compatible) |
| Workflow | n8n optional |
| Reverse Internet Access | Cloudflare Tunnel |
| Deployment | Docker Compose |
| Primary Browser | Google Chrome |
| API Contract | REST/JSON + WebSocket; OpenAPI generated by FastAPI |
| Authentication | JWT access token + refresh token, httpOnly secure cookie for browser session where practical |
| Authorization | RBAC |
| Observability | Structured JSON logs + Prometheus-compatible metrics + health endpoints |

### 2.1 Important technology rule

AI providers/models must never be called directly from UI code. All AI capabilities are accessed through backend adapters/interfaces.

The application must not hard-code the Drug Complaint Form, one AI Role, one LLM, one STT engine, one TTS engine, or one vector implementation into business logic.

### 3.1 Runtime principle

Synchronous conversation path:

```text
Browser microphone
  → Realtime Gateway
  → STT
  → AI Orchestrator
  → RAG Service when required
  → LLM
  → TTS
  → Browser
```

Form extraction may run incrementally after each final transcript segment and/or after an AI turn. Heavy ingestion/OCR/embedding/report jobs must use asynchronous workers.

n8n is never required for the synchronous conversation-critical path.

# 6. AI Provider Abstraction

All AI capability interfaces must be explicit.

```python
class STTProvider(Protocol):
    async def transcribe(self, audio: AudioInput, language: str | None) -> STTResult: ...

class LLMProvider(Protocol):
    async def generate(self, request: LLMRequest) -> LLMResult: ...

class EmbeddingProvider(Protocol):
    async def embed(self, texts: list[str]) -> list[list[float]]: ...

class RerankerProvider(Protocol):
    async def rerank(self, query: str, documents: list[str]) -> list[float]: ...

class TTSProvider(Protocol):
    async def synthesize(self, text: str, language: str, voice: str | None) -> AudioResult: ...

class OCRProvider(Protocol):
    async def extract(self, document: DocumentInput) -> OCRResult: ...
```

Each provider must expose:
- model name
- model version
- health status
- capabilities
- timeout
- error category
- metrics

Model configuration is loaded from DB/environment and cached safely.

# 7. Recommended Model Baseline

These are implementation defaults, not hard-coded dependencies. Every model must be replaceable through the adapter layer.

### 7.1 STT

Default candidate: `faster-whisper` using a multilingual Whisper model appropriate for available hardware.

Requirements:
- Thai, English, Chinese
- language detection or explicit language
- timestamps
- segment-level confidence when available
- VAD
- streaming/chunked mode for live audio where supported

If the selected model does not provide sufficiently good Thai/Chinese quality, it may be replaced without changing the STT interface.

### 7.2 LLM

Default candidate: `Qwen3-8B` instruct-class model or equivalent 4B–8B multilingual instruct model validated by benchmark.

Requirements:
- structured JSON output
- multilingual conversation
- instruction following
- tool/function calling if supported
- configurable context window
- local inference

Use a dedicated model server such as vLLM or llama.cpp-compatible runtime behind an adapter. Do not expose the model server directly to Internet.

### 7.3 Embedding

Default candidate: `BAAI/bge-m3` because the system requires multilingual retrieval. Vector dimension must be read from the actual model configuration and stored consistently.

### 7.4 Reranker

Optional default candidate: `BAAI/bge-reranker-v2-m3`.

Use only when benchmark demonstrates improved retrieval quality enough to justify latency/resource cost.

### 7.5 TTS

Use a local TTS adapter. Initial candidate: Kokoro or another local multilingual TTS implementation that passes Thai/English/Chinese voice-quality tests.

If one local model cannot support all three languages adequately, the adapter may route languages to different models while preserving one application-level TTS interface.

### 7.6 OCR

Initial candidate: PaddleOCR. OCR must support image input and scanned PDFs.

## 8.1 Role schema

```json
{
  "role_id": "uuid",
  "name": "Drug Complaint Intake",
  "description": "รับเรื่องร้องเรียนยาเสพติด",

  "allowed_languages": ["th", "en", "zh"],
  "conversation_objective": "collect_form_data",
  "form_version_id": "uuid",
  "knowledge_collection_ids": ["uuid"],
  "llm_model_config_id": "uuid",
  "stt_model_config_id": "uuid",
  "tts_model_config_id": "uuid",
  "safety_policy": {},
  "greeting_policy": {},
  "closing_policy": {},
  "active": true
}
```

## 8.2 Prompt versioning

Prompt lifecycle:

```text
DRAFT → PUBLISHED → SUPERSEDED
```

A published version is immutable. Editing creates a new version.

At session creation, persist:
- role ID
- role version
- prompt version
- form version
- model configuration versions
- RAG collection versions/IDs

This guarantees replay/audit consistency.

## 8.3 Prompt composition

The effective prompt must be constructed from controlled layers:

```text
System policy
+ Role system message
+ Safety policy
+ Conversation objective
+ Form extraction rules
+ Retrieved RAG context
+ Conversation history
+ Current user utterance
```

Retrieved RAG text must be explicitly marked as untrusted source content and must not override higher-priority system policies.

# 9. Conversation State Machine

```text
CREATED
  ↓
READY
  ↓
GREETING
  ↓
LISTENING ↔ THINKING ↔ SPEAKING
  ↓
COLLECTING
  ↓
CONFIRMING
  ↓
COMPLETED
```

Exceptional states:
- PAUSED
- DISCONNECTED
- FAILED
- ABANDONED
- ESCALATED

The state machine must be persisted.

A caller can provide multiple fields in one utterance. The extraction engine must update all supported fields from one segment rather than asking redundant questions.

# 10. Audio Pipeline

## 10.1 Live microphone

Browser:
1. request microphone permission
2. capture audio using MediaRecorder/Web Audio API
3. encode to supported format
4. stream small chunks to Node.js WebSocket
5. gateway binds stream to authenticated session
6. STT produces interim/final segments
7. final segments are persisted

The exact codec may be selected based on Chrome compatibility; server must normalize audio before STT if necessary.

## 10.2 Audio file

```text
Upload
 → virus/type/size validation
 → object storage
 → create AudioAsset
 → async transcription job
 → STT
 → transcript segments
 → extraction
 → form values
```

Maximum upload size must be configurable.

Never trust the filename or client MIME type; inspect content where practical.

# 14. Form Extraction Engine

Extraction must use structured output, not free-form text parsing alone.

## 14.1 Extraction request

```json
{
  "session_id": "uuid",
  "transcript_segment_ids": ["uuid"],
  "form_version_id": "uuid",
  "fields": [
    {
      "key": "subject_age",
      "type": "integer",
      "meaning": "อายุของบุคคลที่ถูกร้องเรียน",
      "priority": "high"
    }
  ]
}
```

## 14.2 Extraction result

```json
{
  "field_key": "subject_age",
  "value": 35,
  "status": "PROPOSED",
  "confidence": 0.96,
  "evidence": [
    {"segment_id": "uuid", "quote_span": [10, 23]}
  ],
  "reason": "Caller explicitly stated age",
  "model_config_id": "uuid"
}
```

The backend must reject extraction results that:
- reference unknown field keys
- violate field type
- fail validation
- have no evidence for fact-like values

## 14.3 No-guessing enforcement

Prompt rules alone are insufficient. Backend validation must enforce:

```text
No evidence → no factual value
Ambiguous evidence → CONFLICTED / PROPOSED, not CONFIRMED
Explicit denial → REJECTED / NOT_PROVIDED
Human correction → CORRECTED + preserve original
```

# 15. Dialogue Question Selection

The Orchestrator calculates missing-field priority.

Priority order:

```text
Critical > High > Medium > Low
```

The engine should group related questions where natural, e.g. person identity/description or location details, but must avoid long confusing multi-part questions.

It must skip fields that are:
- already confirmed
- explicitly not provided
- irrelevant to current case type

It may revisit conflicted fields for clarification.

A configurable maximum number of follow-up attempts per field should prevent loops.

# 16. RAG Architecture

## 16.1 Collections

A Role can reference multiple collections.

Effective retrieval scope:

```text
Global allowed collections ∩ Role collections ∩ active document versions
```

## 16.2 Ingestion pipeline

```text
Upload
 → Validate
 → Store original
 → Parse
 → OCR if required
 → Normalize
 → Detect language
 → Chunk
 → Embed
 → Store chunk + vector
 → Activate index
```

Document status:

```text
UPLOADED
PROCESSING
READY
FAILED
DISABLED
DELETED
```

## 16.3 Chunking

Chunk by semantic boundaries where possible. Preserve:
- document ID
- document version
- collection ID
- page
- section
- source filename
- language
- chunk index

Chunk size and overlap must be configurable and benchmarked.

## 16.4 Retrieval

Baseline:
1. normalize query
2. apply collection/metadata filters
3. vector similarity search
4. optional lexical/hybrid search
5. optional reranking
6. apply threshold
7. return top-k
8. record retrieval trace

## 16.5 Grounded generation

If retrieval score is below threshold or no result is available, the Orchestrator must not manufacture an answer. It should return a configured uncertainty response.

RAG result format:

```json
{
  "request_id": "uuid",
  "results": [
    {
      "document_id": "uuid",
      "document_version_id": "uuid",
      "collection_id": "uuid",
      "chunk_id": "uuid",
      "filename": "policy.pdf",
      "page": 3,
      "section": "...",
      "text": "...",
      "score": 0.87
    }
  ]
}
```

The AI response record stores the IDs of retrieval results used.

# 17. RAG Service API

Base path: `/api/v1/rag`

### POST `/retrieve`

Request:

```json
{
  "request_id": "uuid",
  "session_id": "uuid",
  "query": "...",
  "ai_role_id": "uuid",
  "ai_role_version": 3,
  "language": "th",
  "allowed_collection_ids": ["uuid"],
  "metadata_filters": {},
  "top_k": 8,
  "similarity_threshold": 0.65,
  "rerank": true

```

Response: HTTP 200 with `request_id`, results and provenance.

Authentication: internal service token/mTLS-ready design. For Phase 1, use a strong internal bearer token stored in Docker secret/environment and network isolation.

The RAG API must not expose arbitrary SQL/vector queries.

# 22. Security Architecture

## 22.1 Network

Only these services are externally reachable through Cloudflare:
- reverse proxy / web frontend
- API routes required by frontend
- WebSocket route

Never expose directly:
- PostgreSQL
- Redis
- MinIO admin
- LLM server
- STT/TTS servers
- internal RAG service
- n8n admin UI unless explicitly secured and intentionally published

## 22.2 Authentication

Use JWT-based authentication with short-lived access token and refresh mechanism.

Passwords must be hashed using Argon2id or equivalent modern password hashing.

## 22.3 Authorization

RBAC:

| Role | Main permissions |
|---|---|
| Viewer | read permitted sessions/reports |
| Agent | session/form/transcript/human correction |
| Supervisor | Agent + dashboard/reports/quality |
| Admin | all configuration/user/model/RAG functions |

Authorization must be enforced server-side.

## 22.4 Sensitive data

Sensitive fields must have a classification. Logs must never contain raw passwords, tokens or unnecessary sensitive caller data.

Phone numbers and contact identifiers should be masked in operational logs.

## 22.5 File security

Uploaded files:
- validate extension and content type
- enforce configurable size limit
- store outside executable paths
- generate server-side object key
- prevent path traversal
- optionally virus-scan
- never execute uploaded content

# 34. AI Safety / Grounding Policy

The application must implement a layered policy:

1. system prompt policy
2. role-specific policy
3. structured extraction schema
4. backend validation
5. RAG retrieval threshold
6. provenance persistence
7. human review

For factual knowledge questions:

```text
Enough evidence → answer using evidence
Insufficient evidence → uncertainty response
Conflicting sources → report conflict / request clarification
```

For complaint data:

```text
Explicit caller evidence → PROPOSED
Caller confirms → CONFIRMED
Human edits → CORRECTED
No evidence → NOT_PROVIDED/EMPTY
Contradiction → CONFLICTED
```

AI must not convert allegation into verified fact in the wording of its own response.

# 45. Final Implementation Principle

The system is intentionally designed around this invariant:

```text
             AI Role
                +
          System Message
                +
         Conversation State
                +
          Dynamic Form
                +
       Authorized RAG Knowledge
                +
       Pluggable AI Models
                ↓
        AI Call Center Agent
                ↓
     Grounded + Structured + Traceable
                ↓
       Human Review / Case
```

**Changing the AI's role must be a configuration operation, not a software deployment operation.**

**Changing the AI model must be a model-configuration operation, not a business-logic rewrite.**

**Changing the Knowledge Base must not require changing the AI Agent code.**

**Changing the Form must not require changing the frontend business logic.**

This is the core architectural contract for the implementation.
